# 日志文件导出实测报告（v1.8.1）

- 测试日期：2026-11-27
- 测试工具：`perf/FileExportBench`（net8.0 控制台基准，直接编译共享生产代码 `android/BotwExtractor/Ui/*.cs`；"旧实现"为 v1.5 导出管线的逐字副本）
- 原始输出：`perf/file-export-bench-output.md`
- 被测路径：设置页「导出预览 → 导出 .log」所走的真实链路 —— `LogExporter.WriteTo` 流式格式化 → UTF-8(无 BOM) 64 KB `StreamWriter` → 新建文件写入并关闭（等价于 SAF `CreateDocument` 拿到目标后写内容）

## 2. 测试方法

- 数据：固定种子（20261127）生成，时间戳单调递增、跨度 3 小时，5 种典型消息轮换（提取进度 / 校验通过 / 跳过损坏文件 / exefs 统计 / 英文 chunk），级别 INFO 为主、混 WARN/ERROR。
- 量级：0 / 100 / 500 / 1,000 / 5,000（应用 `LogStore` 环形容量上限）/ 20,000 / 100,000 条。
- 计时：每量级 1 次预热 + N 次计时（0–1,000 条 200–300 次；5,000 条 100 次；20,000 条 20 次；100,000 条 5 次）。
- 统计：整个基准重复 **5 轮**，下表取"每轮 p50 的 5 轮中位数"，另给出"每轮最小值再取中位数"作为纯写入参考。
- 文件口径：每次导出都**新建文件、写完后删除**（等价于用户每次导出新建一个 `.log`），因此计时包含文件创建、缓冲刷新、关闭（以及 Defender 对新文件的扫描）。
- 阶段口径：
  - **预览格式化**：`LogExporter.Format` → 内存字符串，即导出预览对话框里渲染的完整内容。
  - **旧实现导出（v1.5）**：先把全部内容拼成一个巨型字符串，再用 1 KB 缓冲 `StreamWriter` 一次写入文件。
  - **现实现导出（v1.8.1）**：`WriteTo` 直接把每条记录格式化进 64 KB 缓冲区并流式写入文件，全程不产生完整字符串。
- **正确性门禁**：每个量级都校验"现实现写出的文件字节 == 旧实现写出的文件字节 == `Format()` 的内存输出"，不一致立即抛异常终止。

## 6. 结果分析

1. **应用真实上限（5,000 条）导出是"瞬时"级**：输出 334.5 KB，端到端 p50 **5.56 ms**、最快 **0.90 ms**；换算约 90 万条/秒（p50）/ 556 万条/秒（min）。用户在设置页点"导出"后感知不到等待。
2. **固定开销占比很大**：0 条日志导出仍要 **0.15 ms**（创建 + flush + 关闭空文件）。≤1,000 条时导出时间几乎全被这部分与文件系统/杀软扫描占据，算法差异被 I/O 掩盖 —— 这也是 500/1,000 行"旧实现 p50 反而 4–5 ms"的原因：p50 落在 Defender 对新文件同步扫描的样本上，而非算法本身（对应 min 仅 0.38–0.56 ms）。
3. **数据量越大，流式实现的优势越稳定**：20,000 条 p50 9.86 → 5.78 ms（1.7x），100,000 条 45.66 → 15.56 ms（**2.9x**，min 口径 38.75 → 15.14 ms，2.6x）。原因是旧实现要先构造一个 6.7 MB 的 UTF-16 巨型字符串（峰值 50 MB 分配）再经 1 KB 缓冲写出，而现实现直接流式落盘。
4. **吞吐随数据量上升并趋于上限**：现实现 p50 吞吐从 500 条的 69.8 MB/s 升到 100,000 条的 **420.8 MB/s**（min 口径 432.5 MB/s），接近该 SSD 上 .NET 顺序小写入的实用上限；瓶颈已不是序列化（6.6 MB / 15 ms）。
5. **预览阶段的成本需要注意**：预览是内存字符串，≤5,000 条仅 0.68 ms / 1.34 MB，无压力；但若把日志容量放大到 100,000 条，预览一次要 18.27 ms 且 **分配 26.87 MB**，在大内存压力机型上可能触发 GC —— 当前 5,000 条上限下不存在该问题。
6. **噪声来源与口径差异**：Windows Defender 实时保护开启时，每次"新建文件 + 关闭"都会触发同步扫描，导致同一档位 p50 在 0.5–6 ms 间跳动（表 §3 的 5,000 条 p50 5.56 ms 与 §4 的 min 0.90 ms 差值即来源于此）。因此本报告同时给出 p50（用户带杀软环境下的典型值）与 min（纯写入成本），两者都可信，**不应混用**。

## 7. 结论与建议

- 以当前产品形态（`LogStore` 上限 5,000 条），**导出不是性能热点**：PC 端 1–6 ms，真机预计在数十毫秒量级（SAF 文档创建 IPC + 闪存 fsync 为主）。无需为导出再做优化。
- **保留 v1.6 的流式实现**：它把导出分配从"随条数线性（最高 50 MB）"降到恒定 0.3–0.4 MB，并在压力场景（10 万条）快 2.6–2.9x；这对 Android 上避免大对象堆分配与 GC 停顿有实际价值。
- **不要回退到"整段字符串 + 小缓冲"写法**：旧实现在 100,000 条时仅字符串就有 ~13 MB（UTF-16）峰值，且写盘路径多一次完整拷贝。
- 若未来放开日志容量上限（例如 50,000+ 条），建议：预览走分页 / 截断展示，导出继续流式（现状实现可直接支撑）；同时把导出改为在后台线程执行（现状已如此）。
- **真机数据缺口**：本轮只覆盖 PC 运行时。若需要真实 Android 端到端耗时（含 SAF），需要连接设备跑同一份 `LogExporter` 并记录 `SystemClock.elapsedRealtime()`，可作为下一步补充。

## 8. 复现命令

```bash
# 构建并运行（Release）
dotnet build perf/FileExportBench/FileExportBench.csproj -c Release
dotnet perf/FileExportBench/bin/Release/net8.0/FileExportBench.dll
```

```powershell
1..5 | ForEach-Object {
  dotnet perf/FileExportBench/bin/Release/net8.0/FileExportBench.dll *> "run$_.md"
}
```

## 9. 表格口径备注

- 「p50」= 每轮 N 次计时的中位数；表 §3 为 5 轮 p50 的中位数。
- 「min」= 每轮最快一次的耗时；表 §4 为 5 轮 min 的中位数。
- 吞吐 = 输出字节数 ÷ 耗时；条目速率仅对非 0 条有意义。
- 所有量级均通过字节一致性校验（新实现 / 旧实现 / 预览三者逐字节一致），失败会中止基准。
